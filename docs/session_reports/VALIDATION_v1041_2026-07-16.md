## PART A — the false-failure fix (DONE + PROVEN on a clean box)

v1.0.40 *falsely* RED-gated a healthy install: the `$gatewayInstall` block tee'd three
best-effort `systemctl --user` lines to `/tmp/openclaw-install.log`, which is created
**root-owned** by the npm-install step (`> >(tee /tmp/openclaw-install.log)` runs as root). The
block runs as **clawuser**, so under `set -o pipefail` the tee failed "Permission denied" → the
block surfaced exit 1 → the PowerShell throw wrongly reported *"did not create the unit"*.

**A1 — dropped the redundant tee.** Removed `LOG=`/`mkdir` and changed the three lines from
`… systemctl --user … 2>&1 | tee -a "$LOG" || true` to `… 2>&1 || true`. `Invoke-WslBash` already
captures every stdout/stderr line into `C:\ProgramData\ClawFactory\install.log`, and `2>&1` still
merges each call's stderr into the block's stdout, so which (if any) systemctl call fails stays on
record.

**A2/A3 — gate on the invariant, not the block exit.** In the `$rcGateway -ne 0` branch: `exit 90`
(ownership guard) still throws the exact ownership case; for any other non-zero,
`Invoke-WslBash 'test -f …/openclaw-gateway.service'` — if the unit is **missing**, throw the
now-accurate *"did not create the unit (verified missing with test -f)"*; if it **exists**,
`Write-Log WARN` and defer the verdict to the `/status` health poll (the authority).

**PROVEN by the clean-box run (cfv-0716r, `diag-out.txt` §2.5, verbatim):**

```
[wsl:clawuser out] [gateway-install] openclaw gateway install --force --port 8787
[wsl:clawuser out] Installed systemd service: /home/clawuser/.config/systemd/user/openclaw-gateway.service
[wsl:clawuser out] [gateway-install] Gateway service active (attempt 1)
[wsl:clawuser exit] 1                    <- block STILL exits 1 (the tee was NOT the sole cause)
[wsl:clawuser exit] 0                    <- my new `test -f`: the unit EXISTS
[2026-07-16 21:59:56] [WARN] gateway-install block exited 1, but the unit file
  /home/clawuser/.config/systemd/user/openclaw-gateway.service exists (verified with test -f).
  This is the known-benign non-zero block exit (best-effort systemctl in a no-user-bus context);
```

Read plainly: the block still exits 1 (so **A2 is the load-bearing fix**, not A1 — the pipefail

### The new blocker — root cause (verbatim + code)

`diag-out.txt` §2.5, the post-gateway sequence (verbatim):

```
[wsl:clawuser err] Config overwrite: /home/clawuser/.openclaw/openclaw.json (… 8787 -> 8788 …)
[wsl:clawuser err] [chatCompletions-restart] WARNING: gateway did not respond within 12s after restart
[wsl:clawuser exit] 1
[2026-07-16 22:01:40] [WARN] Step-EnableChatCompletions returned exit=1. …
```

and the honest verdict:

```
INSTALLER_DONE=failure reason=Failed to install the chatCompletions gating proxy (Blocker 1).
The installer rolled the gateway back to 8787; ClawChat turns would be UNGATED - do not ship this install.
```

- `Step-EnableChatCompletions` (setup.ps1:2173) restarts the gateway and waits **12s** (`for i in
  1..6; sleep 2`). Non-fatal (WARN only) — but a symptom of the same too-short window.
- The **fatal** is `Step-InstallChatProxy` (setup.ps1:2337 → `resources/install-chat-proxy.sh`, run
  as root). It moves the real gateway to **8788** via a systemd `ExecStart=` drop-in, does
  `su clawuser -c "systemctl --user restart openclaw-gateway"`, then health-checks:
  - **8788 up:** `for i in $(seq 1 15); … sleep 2` → **~30s** (install-chat-proxy.sh:55)
  - **proxy /status 200:** `for i in $(seq 1 10); … sleep 2` → **~20s** (install-chat-proxy.sh:70)
  - either miss → `FATAL … rolling back` → `exit 1` → the throw at setup.ps1:2366.
- The gateway cold-start on a 2-vCPU VM is **~67s** (setup.ps1's own comment: "bound :8787 at
  35.5s, fully ready ~67s"; the `/status` poll was widened 60→120s for exactly this). ~30s/~20s/12s
  are all well under 67s → the restarted gateway hasn't finished cold-starting when the proxy step
  gives up. Secondary risk: the port-move relies on `systemctl --user restart` in the no-user-bus
  install context, whereas the gateway *install* works around that by direct-start.

**Why it was never seen before:** every prior clean-box run RED-gated at the gateway false-failure,
so `Step-InstallChatProxy` had never actually executed on a fresh install. Fixing PART A exposed the
next domino. The installer's fail-closed behavior here is *correct* design — it refuses to ship an
ungated ClawChat path — so this is a genuine install defect to fix, not a check to relax.
