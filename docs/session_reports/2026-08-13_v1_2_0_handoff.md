## 1. One paragraph of context

ClawFactory packages a local AI agent (OpenClaw) inside WSL on Windows with a set of
security guards around it. v1 ships two: **Guard 1**, recoverable deletes, where a file the
agent deletes inside a folder you granted it is held for 30 days instead of destroyed; and
**Guard 2**, approval-gated email, where the agent can compose a message but only a human
can send it. Guards 3 and 4 are unbuilt. The build sequence has a step 7, full validation on
the assembled build, which has NOT happened and is not what this session did.

## 3. The three defects that were fixed

Summarised because the causes generalise; full detail in the close-out.

**D1, `82f1051`. Neither guard could install.** `Invoke-WslBash` base64-encoded its whole
script onto the command line, capping every caller at the Windows 32,767-character
`CreateProcess` limit. Guard 1 needed 84,692; Guard 2 needed 153,912. Now streams over
stdin. *Generalisable lesson: the limit was already known in that same file and worked
around at exactly one call site, and four later steps inherited the broken path.*

**D2, `fe2bdc5`. Guard 1 intercepted nothing and claimed it had.** OpenClaw prepends the
running node binary's directory to PATH *after* applying `tools.exec.pathPrepend`, and node
lives in `/usr/bin` beside the real `rm`, so the quarantine wrapper could never win. A real
agent turn destroyed a file and then told the user it was safely held for 30 days. Fixed by
`dpkg-divert` of `/usr/bin/rm`, which removes PATH from the question and also closed the
`/bin/rm` bypass. Root passes straight through so the distro cannot be bricked, and
uninstall restores the stock binary.

**D3, `d75bdcc`. Restarting one guard disabled the other.** Both units declared
`RuntimeDirectory=clawfactory`, so systemd deleted `/run/clawfactory` when either stopped,
taking the other guard's sockets with it, while `systemctl` still reported `active`.
Fixed with `RuntimeDirectoryPreserve=yes`.

## 4. OPEN ITEM 1: Studio is a scaffold (D4). Not fixed. Needs a decision.

**This is the largest gap between what the product says and what a user can do.**

The installed Studio v0.1.0 shows this on Approvals, Recently deleted, and Email settings:

> "Studio backend unreachable. This panel is not wired in the desktop shell scaffold yet.
> Studio is being rebuilt as a native app; the Workspace (grants) panel is fully functional."

Confirmed structurally: no Studio backend is listening at all. Only the chat proxy (8787),
gateway (8788) and browser control (8790) are bound. Only Workspace/grants works.

Why it matters:

1. **Guard 2's approval card is the product.** The claim is "every message waits for you".
   The surface where a user reads and approves a message does not function.
2. **Guard 1's restore route is dead.** The agent tells users, in its own words, that a
   deleted file "can be restored via Studio, Recently deleted". That panel shows the error
   banner. The file genuinely IS recoverable through the root channel, but the route the
   product names does not work.
3. It removed the credential intake path this validation was designed around.

**The decision:** wire Studio, or change every piece of copy that names those panels,
including the agent's own wording. Leaving it as-is is the one option that isn't defensible,
because the product currently tells users to go somewhere that errors.

The Studio source lives in a separate private repo (`BuzzardsBay/ClawFactory-Studio`, local
clone `C:\Users\bmcki\ClawFactory-Studio`). The panels EXIST in that source
(`frontend/src/pages/send/SmtpSetupPage.tsx`, `ApprovalsPage.tsx`, `RecentlyDeletedPage.tsx`)
but the packaged desktop shell does not route to them and ships no backend. So this is
plumbing, not new feature work. Do not assume the panels need writing from scratch.

## 5. OPEN ITEM 2: the agent cannot find its own email capability (#199a)

On a fresh install with the shipped SOUL and persona, asked in plain language to send an
email, the agent did **not** discover `clawfactory-send`. It also did not improvise a
transport (no sendmail, curl, smtplib), which is the safe half.

Two separate questions were asked deliberately, and both answers are recorded. Shipping a
capability the agent cannot find is a product decision, not a bug to patch silently. Options
are roughly: mention it in the persona or orchestrator prompt, document it for the user, or
accept that it is invoked explicitly.

## 6. What is proven, and how, so nobody re-litigates it

- **Guard 1 routing.** A real agent turn, instructed in natural language to delete a file in
  a granted workspace, routed it into quarantine. The index carries the file with sha256,
  original path, `requestedBy: clawuser`, 30-day expiry. Restore is byte-exact with correct
  ownership, and refuses a tampered payload.
- **Guard 2 end to end.** A real message crossed from Gmail to a third-party Outlook mailbox
  and landed in the Focused inbox. Gmail queue ids are in the broker log.
- **The staging property, the strongest single result.** A message was approved, then the
  source attachment on disk was rewritten to `B-BYTES-TAMPERED` before the send executed. The
  delivered attachment read `A-BYTES`. The bytes the user approved are the bytes that left,
  verified in a third party's mailbox.
- **The gate holds.** 17 requests were queued across the session; exactly 2 were sent.
  Everything else was denied, expired or killed.
- **No credential leakage.** The real app password appeared in no log, receipt, journal,
  argv, environ or process listing. Confirmed twice, with a working positive control.
- **Reboot persistence.** Units, timers, sockets (with modes), firewall shape and the Guard 1
  divert all return after a restart.

## 7. Known bypasses. Do not describe the product as if these are closed.

1. **The agent can exfiltrate to the model provider.** The gateway runs as the agent's uid and
   holds the provider credential; anything the agent reads can leave over allowlisted 443. No
   v1 guard touches this. Card #197.
2. **Door 2, full-path `.mjs` execution.** Agent and gateway share a uid. Accepted v1 residual.
3. **Deletes that are not `rm`.** `unlink`, `find -delete`, `fs.rmSync`, `os.remove`, and
   truncation via `>` all bypass the wrapper. Measured, not assumed. The divert closed
   `/bin/rm`; it did not close these.
4. **Root is out of scope by design.** The wrapper passes uid 0 through so the distro works.
5. Co-hosted addresses re-open 443, never an SMTP port. Allowlisted addresses persist up to
   six hours (card #194). Nothing enforces `read_fetch` in v1. A user who approves without
   reading is not protected, and in this build has no working surface to read in.

### The claim sentences that the evidence supports

> Your agent can write an email. It cannot send one. Every message waits for you, and
> approving it sends exactly that message, once.

> When your agent deletes a file in a folder you granted it, the file is held for 30 days and
> you can put it back. This covers deletion by name, which is how deletion is ordinarily
> expressed; it does not cover every possible way a program can destroy a file.

Both must carry this boundary wherever the mechanism is described:

> This covers email. It is not a claim that no data can leave your machine: your agent talks
> to a hosted AI model, and anything it can read it can send there.

**Never write that data cannot leave the machine without approval.** It can. Guard 2 gates
email; it does not gate egress. Neither sentence may currently be paired with any claim about
Studio (section 4).

```bash

```

**Validate on a clean Azure box.** Repin `$Sha256` and `$ExpectBytes` in
`validation/interim-v120-validate.ps1` to the new artifact first, then:



```bash
powershell -NoProfile -ExecutionPolicy Bypass -File .\validation\job3-teardown.ps1 -VmName cfv-157 -ResourceGroup clawfactory-validation -OutDir "C:\Users\bmcki\ClawFactory-Secure-Setup\validation-runs"
```

### Environment facts that will otherwise cost you an hour

- DSv5 quota in westus2 is **0**. Use `Standard_D2s_v4`. The job prompt says v5; it is wrong.
- Use image `clawfactory-win11-baseline-v2`, not the v1 image.
- The storage account has containers `installers` and `logs` only. A harness must create its
  own and verify uploads by byte count, because **an `az` failure does not stop a script**.
- `az vm run-command` runs as SYSTEM and **cannot touch WSL at all**
  (`WSL_E_LOCAL_SYSTEM_NOT_SUPPORTED`). Anything WSL-side needs an interactive session; that
  is what `interim-v120-runner.ps1` is for, started via auto-logon.
- The installer sets `[automount] enabled=false` by design, so `/mnt/c` does not exist in the
  distro. A probe that needs it only works on a broken install. Use the `\\wsl$` 9p path.
- `/tmp` in the distro is tmpfs under systemd and is wiped by a restart. Use `/var/tmp` for
  anything that must survive.
- `validation/job3-teardown.ps1` has a latent `$PSScriptRoot`-empty bug; always pass
  `-OutDir` explicitly.
- **Deallocate the VM at every handoff to a human.** One was left running ~64 hours during
  this session, about $6 to $7 for nothing.

### Validation discipline that actually caught things

Sixteen bugs in the test harness were found during this session, and every one of them
produced output that looked like a real result. The two habits that caught them:

- **Every block assertion carries a control that must fail in the same run.** A test whose
  control does not fail is a void result, not a pass.
- **Prove liveness by the thing itself, not by a status report.** Asserting
  `systemctl is-active` reported PASS for a broker whose socket had been deleted, which is
  what let D3 hide for a whole phase.

The sharpest example: a credential-leak scan piped `ps` into `grep -F -- "$SECRET"`, which
put the secret on grep's own command line where `ps` captured it. The scan reported exactly
one hit that WAS the scan, indistinguishable from a real credential leak, in the one test
whose entire purpose is finding one.
