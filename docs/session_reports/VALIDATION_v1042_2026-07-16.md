# Clean-install validation v1.0.42 — RELEASE GATE: RED (root cause changed again) — 2026-07-16

**Top line.** The release gate is still **RED and the headline isolation claim is still NOT
proven** — but the v1.0.42 clean-box run (cfv-0716s) moved the diagnosis forward in two important
ways. First, **PART A's premise is CONFIRMED**: the ~67s gateway cold start is real and the 120s
standard clears it — the main `/status` poll caught the gateway cold-starting (`exit 7,7,7,7,28,28,28`
= curl connection-refused then timeout) and then reaching healthy (`exit 0`), and the new
`Step-StageGatewayHelper` staged the shared helper cleanly. Second — and this is why the gate is
still RED — **the remaining blocker is NOT a too-short timeout at all; it is that the gateway
*restart* itself is unreliable in the no-login install context.** `Step-EnableChatCompletions`
returned `exit=1` **even with the new 120s window**: after its `systemctl --user restart
openclaw-gateway`, the gateway did not respond within 120s — i.e. the restart took the gateway down
and it did not come back. The fatal chatCompletions-proxy step (`Step-InstallChatProxy`) rolls back
for the same underlying reason. Per the session rule (install gate fails → STOP and report), I
stopped at the gate and did not iterate further on the box.

This is the A2 branch I did not take: the prompt offered "assert the user manager is up (fail loud)
**OR** make the restart use the same robust direct-start path the gateway install uses." I took the
assert branch; the evidence now shows the assert is not sufficient — the gateway install comes up
reliably via `openclaw gateway install --force` (its own start), while every *restart* step leans on
`systemctl --user restart`, which is the fragile link. **v1.0.43 must harden the restart itself.**

The probe was blind to the exact `[chat-proxy]` failure line (its Task 2.5 only grepped the
gateway-install section), so this run could not say whether `install-chat-proxy.sh` failed on the
user-manager assert, the 8788 health-wait, or the proxy `/status`. **That gap is now fixed** (probe
commit `369d3ed`): the next run captures the `[linger]`/`[gateway-helper]`/`[chat-proxy]` detail.

VM cfv-0716s: provisioned, installed, torn down clean. License slot freed (Task H). ~$0.35.

### The single standard
`resources/gateway-wait.sh` — `wait_for_gateway_healthy <port> [timeout=120] [as_user]` (wall-clock
bounded — a cold gateway can cost `--max-time` per probe, so it counts real elapsed, not accumulated
sleep; breaks on first HTTP 200) + `assert_user_manager_ready <user>`. Staged to
`/usr/local/lib/clawfactory/gateway-wait.sh` by a new `Step-StageGatewayHelper` (right after the
gateway runtime install, before the two steps that source it). Sourced by `install-chat-proxy.sh`
(#4/#5) and `$script9b` (#3). PS-only sites (#7 smoke, #8 launcher) widened in place to the same
120s with comments pointing at the helper. Bundled in `.iss` + asserted in Step-Preflight.
Unit-tested locally: rc=1 wall-clock-bounded at 7s on a dead port; rc=0 instant on a healthy
listener.

site's restart is a bare `systemctl --user restart` with no `XDG_RUNTIME_DIR` and no assert). The

## Recommended next job (v1.0.43)

Harden the gateway **restart**, not the timeouts (those are done). The gateway *install* comes up
reliably via `openclaw gateway install --force` (its own start); every *restart* step
(`Step-EnableChatCompletions`, `install-chat-proxy.sh`) leans on `systemctl --user restart`, which
does not reliably bring the gateway back in the no-login WSL install context. Options, cheapest
first, using the now-instrumented probe to confirm the exact `[chat-proxy]` failure:
1. Give `Step-EnableChatCompletions`'s restart the same `XDG_RUNTIME_DIR=/run/user/$(id -u clawuser)`
   the gateway-install block uses (it currently has none), and call `assert_user_manager_ready`
   there too.
2. If a `systemctl --user restart` with a healthy user manager still doesn't rebind the gateway,
   replace the restart with the gateway install's proven start path (e.g. `openclaw gateway`
   restart, or stop-then-`openclaw gateway install --force`-equivalent honoring the 8788 drop-in),
   so a port change is applied by a mechanism known to bring the gateway up.
3. Consider whether the gateway is being SIGTERM'd by WSL last-session-exit teardown *between*
   Invoke-WslBash calls (linger not holding it) — if so, the fix is to make linger actually hold the
   service, or hold a session across the chat-proxy steps.

Out of scope (future): reducing the *number* of restarts during install (each costs another ~67s
cold start; configure-final-port-then-start-once is an architecture change). Full-path `.mjs` bypass.
